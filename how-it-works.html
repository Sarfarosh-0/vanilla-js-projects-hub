01 — Introduction

A small, open collection of vanilla JavaScript projects

The Vanilla JS Projects Hub is a set of self-contained projects built with HTML5, CSS3, and plain JavaScript. Each project lives in its own folder, opens directly in a browser, and is open to contributions.

It is for people making a first open source contribution as well as experienced developers who want a small, focused place to practise. Every project is also a readable example: no framework, no bundler, no hidden runtime.

This page explains the rules a project must follow, the automation that checks it, how a pull request becomes a live card on the home page, and what to expect during review. If you only read one section before contributing, read Step-by-step flow.

02 — The big picture

Four steps from issue to live project

Every contribution follows the same path. The details change, but the sequence does not.

  1. 1

    Find or create an issue

    Look for open issues labelled good first issue or help wanted, then comment to ask for assignment. Issue claims expire after 7 days if no pull request is opened.

  2. 2

    Fork and build

    Fork the repository, clone your fork, and create a descriptive branch. Add or improve one project folder, keeping every change inside that folder.

  3. 3

    Open a pull request

    Push your branch and open a PR against main. Fill out the PR template, including the AI disclosure. Automated checks run before a maintainer reviews.

  4. 4

    Review, merge, and ship

    A maintainer aims to review within 7 days. After merge, the index is regenerated and the site is deployed to GitHub Pages.

03 — Contribution ladder

Pick the level that fits you today

Contributions of every size are welcome. Start where you are comfortable — you can always move up.

Level 1

Quick fixes

Small, useful changes that need little context:

  • Fix typos and broken links
  • Add missing alt text or accessibility attributes
  • Improve documentation
  • Submit screenshots
Level 2

Improvements

Work inside an existing project and make it better:

  • Fix bugs
  • Optimise code
  • Improve responsive design
  • Add small enhancements
Level 3

New project

Add a brand-new vanilla JS project to the hub:

  • One project folder per PR
  • index.html, README.md, and project.json
  • Relative asset paths only
  • Works on load with zero console errors

04 — Project structure

One folder, three required files

The validator and the index builder both discover projects by their folder contents, so the structure has to be exact.

  • Folder name: lowercase kebab-case, letters only, no numbers — for example pomodoro-timer.
  • Required files: index.html, README.md with a “What I learned” section, and project.json.
  • One project per PR: every change in the pull request must stay inside that single project folder.
  • Relative paths only: use style.css or ./style.css, never /style.css.
file tree 
vanilla-js-projects-hub/
├── pomodoro-timer/
│   ├── index.html
│   ├── README.md
│   └── project.json
├── calculator/
├── scripts/
│   ├── build-index.js
│   └── validate.js
├── index.html
└── style.css

The project.json file

Metadata drives both the README project table and the home page cards. Keep the sample below as a starting point and replace the values with your own.

json 
{
  "name": "Pomodoro Timer",
  "description": "A 25/5 focus timer with start, pause, and reset.",
  "author": "your-github-username",
  "difficulty": "beginner",
  "tags": ["timer", "dom", "setinterval"],
  "requiresApiKey": false,
  "contributors": []
}
name
3–40 characters.
description
Maximum 120 characters.
author
Your GitHub username. It must match the author of the pull request.
difficulty
One of beginner, intermediate, or advanced.
tags
Up to 5 lowercase strings.
requiresApiKey
true or false.
contributors
An array of GitHub usernames. Maintainers update it when a contribution is merged.

05 — Rules and tech constraints

What every project must respect

These rules keep projects portable, safe, and readable for the next contributor.

Pure vanilla only

HTML5, CSS3, vanilla JavaScript (ES6+), and standard browser APIs. No frameworks and no runtime dependencies baked into the project.

No build steps

No Vite, Webpack, Babel, node_modules, or committed minified bundles. Opening index.html must work as-is.

CDN whitelist

Only libraries on the approved list may be loaded from a CDN. The contribution guide names Tailwind CSS (standalone/CDN), Chart.js, Google Fonts, Font Awesome, and Flaticon/Icons8.

cdn-whitelist.json holds the allowed hosts: fonts.googleapis.com, fonts.gstatic.com, cdn.jsdelivr.net, cdnjs.cloudflare.com, cdn-icons-png.flaticon.com, and img.icons8.com. Need another library? Open an issue to request it.

Security and safety

  • No tracking or analytics scripts.
  • No eval() or document.write().
  • No obfuscated JavaScript.
  • No unsafe innerHTML with unvalidated user input.
  • Never commit API keys. Use const API_KEY = "YOUR_API_KEY_HERE"; and set "requiresApiKey": true.

Quality and accessibility

  • Opening index.html works with zero console errors.
  • Semantic HTML and clearly labelled inputs.
  • Descriptive alt text on images.
  • Sufficient colour contrast.

Scoped storage

Prefix every localStorage key with your project folder name, for example pomodoro-timer:settings. Never call localStorage.clear().

Reasonable size

Keep project folders lightweight — typically under 2 MB — and optimise images and SVGs before committing.

Originality and AI disclosure

Submit original work or credit the original authors and tutorials in the README Credits section. Disclose AI assistance in the PR template as none, some, or most, and say which parts. There is no penalty for using AI, but transparency is required.

06 — Automation

The robots that check and publish the hub

Four GitHub Actions workflows keep the repository consistent. Here is exactly what each one does.

Pull requests

validate.yml

Runs on every pull request targeting main, on Node.js 20:

  • Verifies PR scope: changes to .github/workflows/, scripts/, or cdn-whitelist.json are restricted to maintainers, and only one project folder may change.
  • Runs node scripts/validate.js.
  • Runs node scripts/build-index.js --check to confirm the generated README.md table and root index.html are committed and current.
Validation script

scripts/validate.js

Checks each project folder:

  • Folder name is lowercase kebab-case with letters only.
  • index.html, README.md, and project.json exist.
  • Every project.json field follows the rules above.
  • HTML, CSS, and JS contain no absolute local paths, eval(), document.write(), tracking scripts, or probable committed API keys.
  • HTML loads only whitelisted CDN URLs.
After merge

build-index.yml

Runs on every push to main:

  • Runs node scripts/build-index.js.
  • The script reads every project.json and rebuilds the README project table between its markers, plus the root index.html from scripts/templates/index.html.
  • If either file changed, the workflow commits README.md and index.html as github-actions[bot] with a [skip ci] message.
Deployment

pages.yml

Runs on pushes to main and on manual dispatch:

  • Regenerates the landing page.
  • Copies the site into _site, excluding .git, .github, _site, and scripts.
  • Uploads the artifact and deploys it to GitHub Pages.
Housekeeping

stale.yml

Runs daily on a schedule and on manual dispatch. It marks pull requests with no recent activity as stale at day 14, then closes them 16 days later — day 30 overall. Issues are not auto-closed by this workflow.

Generated files are not hand-edited

The root index.html is generated from scripts/templates/index.html, and the README project table is generated from project metadata. After changing a project.json, run node scripts/build-index.js and commit both generated files. Never edit index.html by hand.

07 — Step-by-step flow

Your first contribution, start to finish

The eight steps below come from the contribution guide. New to Git and GitHub? The First Contribution Guide walks through the same flow in more detail.

  1. Find or create an issue

    Check open issues for labels such as good first issue or help wanted and comment to ask for assignment. Claims expire after 7 days if no PR is opened.

  2. Fork the repository

    Use the Fork button on GitHub to create your personal copy.

  3. Clone your fork

    Replace the placeholder with your GitHub username.

    bash 
    git clone https://github.com/<your-username>/vanilla-js-projects-hub.git
cd vanilla-js-projects-hub

  4. Create a descriptive branch

    Never work directly on main.

    bash 
    git checkout -b add-pomodoro-timer

  5. Develop and test your project

    Check all required files, then run the validation script that mirrors the CI checks:

    bash 
    node scripts/validate.js

  6. Commit your changes

    bash 
    git commit -m "Add pomodoro-timer project"

  7. Push to your fork

    bash 
    git push origin add-pomodoro-timer

  8. Open a pull request

    Open a PR against the main branch of this repository. The PR template loads automatically — fill out every section, including the AI disclosure, then create the pull request.

Common mistakes and how to fix them

I made commits directly on main

Move the work onto a new branch, then reset your local main:

bash 
git branch add-my-project
git fetch upstream
git reset --hard upstream/main
git checkout add-my-project
My PR has merge conflicts

Fetch the latest upstream changes, rebase your branch, and resolve conflicts in your editor:

bash 
git fetch upstream
git checkout add-my-project
git rebase upstream/main

# Resolve conflicts in your editor, then:
git add <resolved-file>
git rebase --continue

git push origin add-my-project --force-with-lease
My fork is out of date

Sync main with upstream, or use the Sync fork button on GitHub:

bash 
git checkout main
git fetch upstream
git merge upstream/main
git push origin main
Git says permission denied or the remote is wrong

Check where origin points. If it points at the upstream repository, set it back to your fork:

bash 
git remote -v
git remote set-url origin https://github.com/<your-username>/vanilla-js-projects-hub.git

08 — Review and stale policy

What happens while your PR waits

Reviews are human, so timelines are expectations rather than promises. The stale policy keeps the queue manageable without closing the door.

  1. Day 0 PR opened Automated checks run, then a maintainer picks it up.
  2. Day 7 Review target “I aim to review PRs within 7 days. It's a goal, not a guarantee.”
  3. Day 14 Stale reminder If changes were requested and the PR is inactive, a friendly reminder is posted.
  4. Day 30 Auto-close No activity by day 30 closes the PR. It can be reopened when you are ready.

Issue claims

If you claim an issue but do not open a pull request within 7 days, the claim expires so someone else can pick it up.

Updating someone else's project

Small bug fixes and documentation improvements can be merged directly. Significant redesigns or rewrites notify the original author, who gets a 7-day window for feedback before a decision.

09 — Why this architecture

Simple by design, with honest trade-offs

A static site and a plain folder-per-project layout are not right for every project. They are right for this one.

Advantages

  • Zero build: each project is a set of plain files, and opening index.html is enough.
  • Free hosting: GitHub Pages serves the site from the repository, with no server to maintain.
  • Transparent history: every change, review, and merge stays in git where anyone can inspect it.
  • Low contribution friction: someone can start with a typo fix and finish with a complete project.

Trade-offs

  • Index updates only after merge: a new project card appears when the post-merge workflow runs, not while the PR is open.
  • No server-side features: static hosting means no backend, database, or private secrets.
  • One project per PR: keeping changes isolated makes review easy, but it rules out broad refactors.
  • Strict automation: generated files and metadata have to stay in sync, so contributors run a command before committing.

10 — FAQ

Questions contributors actually ask

Short answers drawn from the contribution guide. The guide wins if anything here drifts.

Can I use AI to help build my project?

Yes. Disclose the level of assistance in the PR template as none, some, or most, and describe which parts were AI-assisted. There is no penalty for using AI, but transparency is required.

Can I use a library that is not on the whitelist?

Open an issue requesting the library. Once the maintainer approves it, adding it is a single-line update to cdn-whitelist.json. Until then, the automated validator will reject the CDN URL.

Can I fix or improve someone else's project?

Yes. Small bug fixes and documentation improvements are merged directly. Significant redesigns or rewrites notify the original author, who gets a 7-day window to give feedback before a decision is made.

Do I need to run the build script?

If you changed a project.json, yes. Run node scripts/build-index.js and commit the regenerated README.md and index.html. The validation workflow runs the same script with --check and fails if the files are out of date.

Can my folder name contain numbers?

No. Folder names must be lowercase kebab-case using letters only, for example pomodoro-timer. The validator checks this pattern.

What happens if my pull request goes quiet?

A friendly reminder is posted at day 14. If there is still no activity by day 30, the PR is closed automatically. Closed pull requests can always be reopened once you are ready to continue.
